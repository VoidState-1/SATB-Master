# SATB Master 项目开发主线

记录日期：2026-11-17。

后续开发围绕自动解题、问题追踪、规则测试和供 AI 使用的 MCP 工具四条主线展开。测试校准规则，日志解释判断过程，推导系统在这些约束下生成并验证答案，MCP 工具让 AI 能调用项目能力开展创作与调试。

## 已确认需求

用户确认的四条主线为：

1. 完善推导系统，实现自动解题。
2. 完善日志系统，高效追踪报错原因。
3. 补充足够的规则测试用例。
4. 开发供 AI 使用的 MCP 工具，包含创作与调试功能。

四条主线均有待开发或继续完善。下面的细化范围与验收方向是对需求的理解和实施建议；题型、工具范围、优先级、量化指标和版本安排在后续任务中确定。

## 完善推导系统并实现自动解题

目标是让系统根据题目条件与和声规则生成可用答案，并解释关键选择。自动解题需要在现有和弦识别、候选推导、乐句分析基础上，进一步处理未完成的题目、生成待填写内容，并通过规则检查验证结果。

当前入口为 [和弦推导](../src/domain/harmony/inference/inferChords.ts)、[完整和声推导与应用](../src/domain/harmony/inference/harmonyInference.ts)；现有流程主要从已有音符推导和弦与乐句结构。实现边界见 [自动分析文档](../Docs/analysis-inference.md)。

建议细化为：

- 明确题目输入、已知条件、允许修改的内容及答案目标。首批可考虑给定旋律或低音补全四部和声，具体题型需另行确定。
- 在调性、和弦功能、节奏、声部进行、乐句和终止式约束下生成候选，搜索整体连贯的解答。
- 区分必须满足的约束与用于比较答案的偏好；规则配置及特例口径与检查系统保持一致。
- 对生成结果重新执行规则检查，保留候选比较与关键选择的依据；存在歧义时允许多个合理答案。
- 区分找到答案、约束冲突、信息不足和搜索达到限制。达到搜索限制不能直接宣称题目无解。
- 提供结果预览与应用，遵守锁定和可编辑范围，并可撤销本次应用。

建议验收方向：在明确的首批题型和经人工校准的题库上，能完成解答、验证规则并解释结果；不能完成时能定位冲突条件或搜索受限的原因。正确率、耗时及题目规模需随题型一起确定。

## 完善日志系统并追踪报错原因

目标是从用户反馈快速还原“当时输入是什么、系统经过哪些判断、为什么得到这个结果”。追踪范围应覆盖程序异常、和声误报、和声漏报及推导失败。

现有 [诊断与调试报告](../Docs/diagnostics-and-debugging.md) 已提供结构化证据、状态跟踪和详细报告，可作为扩展基础。漏报没有现成诊断对象，因此还需要能够按工程范围与目标规则追踪未命中的原因。

建议细化为：

- 关联应用版本、工程 revision、操作或推导批次、规则 ID、配置以及相关音符、和弦和时间范围。
- 跟踪输入与分析事实、规则适用性、命中或跳过原因、状态转移及诊断仲裁，能说明结果为何出现或消失。
- 为推导记录候选生成、淘汰理由、评分、路径选择及停止原因，便于定位错误发生的阶段。
- 为程序异常保留错误堆栈、所属模块与相关操作；统一关联主进程、渲染进程和 Worker 中的相关事件。
- 支持复制或导出足以复现问题的报告，并关联必要的输入快照，减少来回索要信息。
- 控制日志等级、体积、保留期限和性能开销；导出工程内容和本地路径时明确范围，默认保持本地记录。

建议验收方向：面对一次误报、漏报或异常，能够从报告追溯输入、执行路径与原因，并构造最小复现；“规则未启用”“上下文不足”“执行异常”和“确实未违反规则”应有可区分的记录。

## 补充规则测试用例

目标是让规则判断有可核对的音乐学依据，并让后续修改及时暴露误报与漏报。用例数量应服务于语义和场景覆盖。

现有基础包括 [规则测试工作台与用例格式](../Docs/rule-testing.md)、[规则金样本目录](../RuleCases) 和领域测试；仓库中的金样本已接入 [Vitest 批量回归](../src/domain/harmony/testing/ruleCases.test.ts)。

建议细化为：

- 建立规则与用例的覆盖清单，记录规则适用条件、已有场景、预期结论及缺口。
- 每条规则至少覆盖应报与不应报场景，并按实际语义补充边界、特例、缺失上下文、配置与跳过行为。
- 重点覆盖书写音高、调性变化、跨小节、延音与重复音、休止、内外声部及规则之间的相互影响。
- 同时验证诊断规则、位置、相关对象与跳过原因；用跨规则集成用例检查仲裁和覆盖关系。
- 为教材例题记录出处、适用条件与人工解释，先校准预期，再固化为金样本。
- 教材批量转写遵循 [两阶段工作流](../Docs/textbook-case-workflow.md)：先由 Agent 转写、自检并比对推导，确认识读后记录全部规则诊断；再汇总未决判断和同类问题，查证口径依据，交人工审计与方案审阅，通过后修复。
- 教材分析过程仅保留本地忽略目录，Git 只接收已核准并验证的最终版本测试用例。
- 将确认的用户反馈转成最小回归用例，包括反向五八度漏报、小调导音同音异名等已出现问题。
- 随自动解题扩展端到端题库，分别验证输入约束、答案有效性和失败原因。

建议验收方向：规则覆盖清单能明确指出尚缺哪些场景；修复有对应回归用例，批量运行能区分漏报、误报、对象或位置错误与执行异常。测试预期需要独立的人工或教材依据。

## 开发供 AI 使用的 MCP 创作与调试工具

目标是通过 MCP 向 AI 提供可调用的项目能力，让 AI 能读取音乐上下文、执行创作操作、检查结果并追踪问题原因。

建议细化为：

- 创作工具：读取工程、声部、音符、和弦及调性等上下文；创建或修改音乐内容；调用推导与规则检查，并按需要导出成果。
- 调试工具：查询诊断、日志与规则执行过程，追踪误报、漏报和推导失败；运行规则测试，提取或生成最小复现用例。
- 复用现有领域命令、推导引擎、日志与测试运行器，使 AI 操作与应用界面遵守相同的音乐数据约束、锁定与可编辑范围。
- 为调用提供清晰的输入与结构化结果，关联工程 revision 和稳定对象 ID；修改支持批量应用与撤销，并能追溯具体调用。
- 明确工具可访问的工程与资源范围，以及连接、启停和配置方式。首批工具、接入的 AI 客户端与具体接口在实施时确定。

建议验收方向：AI 能完成一次“读取上下文、创作或修改、检查结果”的流程，以及一次“读取问题、追踪原因、运行复现或回归用例”的调试流程；调用结果可核对，修改可撤销，失败原因可追踪。

## 四条主线的协作方式

建议先补齐高风险规则的样本和问题追踪能力，同时推进范围明确的自动解题原型。每次新增推导能力或修复判断问题，都同步完善解释信息与回归用例，逐步扩大可信的解题范围。

MCP 工具复用上述能力，逐步向 AI 开放创作命令、推导、诊断追踪与测试执行，保持应用界面与 AI 调用的行为一致。

后续拆分实施任务时，分别确定首批自动解题题型、首批日志场景、规则覆盖清单、首批 MCP 工具及各自验收标准，再安排版本与优先级。

## 教材答案驱动的 Agent 校准方案

2026-11-19 设计提案。目标是提高程序从完整四声部谱面识别和声、判断终止和诊断声部进行的能力，同时减少人工逐条阅读报告的时间。第一阶段继续独立转写、盲标、比对并保留原始运行结果。拟在第二阶段增加 Agent 查证和按根因修复的权限。下列流程及数值用于讨论与试点，现行审阅约定仍见 [教材工作流](../Docs/textbook-case-workflow.md)。

### 题库、预期与留出

完整连续答案现有 166 份，来自 159 道原题。独立短题 43 份可检验局部连接，93 份片段只评上下文充分的项目。移出的艺术作品另存。新增 100 题有 1,391 个和弦区间，82 题含 112 个结构化终止，另 18 题尚无确定终止标签。另有 9 题因和弦覆盖限制，部分终止标注未能写入规则输入。沿用现有题库索引与逐题记录。[题库分类](../StandardCase/Curated/README.md) · [原题分组](../StandardCase/Curated/2026-11-18-plus100/README.md) · [批次输入与限制](../StandardCase/Expansion/2026-11-18-plus100/README.md)

- 以 `parentQuestion` 分组。同一原题的不同答案、片段、移调副本与派生反例随原题进入同一组。按册别、章节、和声材料和难度分层，可先按约 70% / 15% / 15% 分为开发、验证、封存三部分。开发集用于逐题查错，验证集观察跨题回归，封存集在里程碑版本冻结后评一次。已有样本做过整批分析，检验对新题的泛化能力时，另取从未参与定标或调参的整题。
- 参考按“原题、范围、声部、待判字段”保存。例如同一终止的类型、落点、起点各有独立预期。每个字段记录单一答案、经证据支持的多个答案、明确不存在或未知，以及标注覆盖范围、依据、版本、Agent 判定与人工状态。程序结果另存。多个答案独立定标；若尚待选择全项目的首选标签，则标明主标待定。
- 每轮冻结纯谱面、参考、规则配置、分组、评分口径及版本指纹。盲测只传四声部、拍号和题面明示的调号等条件，清除和弦、局部调性答案、和弦外音角色、乐句和终止标签。先存预测再交给比较器读参考。参考纠错留存前后两版，并让新旧引擎在同一版参考上重跑。

### 三项评测

| 项目 | 每轮主指标 | 用于定位原因的附加结果 |
| --- | --- | --- |
| 和声 | 在可判区间按实际时值计算首选和弦命中率；分别报告和弦身份、转位、局部调性与功能，并报全字段严格命中率。各题等权结果与全体时值加权结果并列。 | 报可判时值占比、程序给出确定答案的覆盖率、边界命中，以及参考仅出现在备选的次数。程序弃权仍占主指标分母。用途、和弦外音仅在有对应预期的字段评分。 |
| 终止 | 从纯谱面推导。对参考覆盖完整的乐句按“类型及落点”一对一匹配，报告精确率、召回率及 F1，另报起止均命中的严格结果。先统一落点和区间右端的拍位表示。 | 给定参考和弦及乐句再跑一次，用两次差异定位上游和声、乐句边界和终止识别的问题。部分覆盖区只评明示字段；未经完整枚举的区域不统计多报。 |
| 规则 | 在已确认转写和适用范围内，分别统计错误、警告的查准率、召回率和每百小节确认误报数。用规则 ID、位置、声部匹配预期。建议单列教学适切性。 | 已知语义下测规则本身，再用推导语义重跑以识别上游连带报错。正确教材答案擅长暴露误报，另配独立标明“应报”的原例、只改一个声部或条件的反例，以及已知“应当放行”的邻近例。合成反例的召回单列。 |

每项列出可判、未知、程序弃权、输入受限、未执行、异常的数量。精确率与召回率注明实际分母，分母为空记为不可估。人工核准集报告程序准确率，Agent 有据判定集单列程序与参考的一致率。报告每次升级新增正确、旧对新错及原因，按原题分组估算指标的不确定性。

### Agent 如何结案，以及何时请人

1. **查一个可核验的事实。** 定位到原谱、音符和前后文。复核者先看谱面和题目独立写预期，再看程序与第一位 Agent 的判断。优先定位工作区斯波索宾教材的版本、书内页、PDF 页、例号或段落。必要时补作者、出版社或院校的一手资料及直接链接。逐项说明原文怎样覆盖本例的调性、转位、声部与例外，并检验最强的相反解释。
2. **按字段分流。** 原谱清楚、理论直接适用、独立复核一致、相反解释已排除且输入可重放的字段，可由 Agent 在本地结案。纯识读纠错以原谱为直接依据。项目允许多解时可以记录有证据的答案集合。疑似教材印错、解释同样成立但软件必须选一项、权威来源冲突、拟改变错误等级或适用标准时，合并成一个人工问题。尚能补裁图或查原文的先交 Agent。
3. **用抽检校准“九成”。** 初期把此档记为“证据充分”。按原题与根因从该档盲抽少量项目，包含程序与 Agent 一致处及没有诊断的连接。记录人工认可数、抽检分母与区间。样本量足够且认可率的置信下界达到 90% 的类别，可减少该类抽检频率。错误、警告优先，建议另计。发现同类系统性错误时暂停该类自动结案，重开受影响记录。独立金标准的评测与这种质量抽检各自统计。
4. **按根因修一次。** 本方案建议在第二阶段按类别预授权。已有明确理论标准、同一根因至少出现在两道独立原题、证据通过上项核验的程序问题，可由 Agent 写最小复现、提交针对触发与放行条件的成对回归，再修改实现。单纯转写或标注错误改候选数据并保留修订。共现的多条下游诊断关联到同一上游根因。每次比较修复前后结果，复跑受影响三项、既有回归及验证集；出现新增的未解释回归时暂缓采用。人工决定一次相同条件下的口径，其他题仍逐题核实适用条件。
5. **交给人工的内容压到一题。** 每个未决根因送一个代表位置、一句需要决定的问题、教材依据、两三个有实质差异的选择和自填框，附受影响原题数。沿用原谱、转写谱与卷帘的拍点联动；题目回答、全谱核准和修复授权分别记录。Agent 结论可直接用于本地开发集。仅经人工核准且重复验证的最终教材用例进入 `StandardCase/Verified/`。

例如 N005，独立标注和给定和弦及乐句的程序结果都支持第 4 小节的属半终止，纯谱面推导漏掉了它。可据此分别调查乐句边界和盲推漏检。教材依据对本题前一拍下属和弦是否计入括线留有余地，人工只需裁定起点。这个选择可以成为后续同类题的标注约定。[首轮审计题与所引教材位置](../StandardCase/Pilot/2026-11-18-decision-round/N005/case.json)

### 开发顺序与验收

| 顺序 | 开发交付 | 验收方式 |
| --- | --- | --- |
| 1. 建立基线 | 做一个批量评测 CLI，将已有本地批次脚本中的纯谱面、给定条件、数据指纹与运行状态提炼为正式入口。复用简写编译、现有和声与终止领域接口、规则调度及隔离运行器。输出可供 Agent 读取的逐题 JSON 和供人阅读的一页摘要。 | 先在开发集分层选约 24 道原题，覆盖上下册、常规连接及复杂和声。相同输入重复运行得到一致判断；替换参考而保持音符不变时，盲推输出不变；未定标签、跳过和异常有各自计数。 |
| 2. 跑第一轮根因修复 | 三项同时建立基线，按受影响独立原题数、严重性与证据选前 2–3 个根因。先处理可能造成下游连带误判的和声或乐句问题，再评涉及的终止与规则。 | 每组交付最小复现、教材依据、正反回归、旧版与新版在同一批题上的增益和退步。另列 Agent 结案率、抽检推翻率、需要人工决定的问题数。 |
| 3. 扩到全库 | 扩到 159 道原题，开发只看开发集个案，验证集在固定节点出汇总结果。逐步补稀有终止和应报反例，冻结发布候选后开启封存评估。 | 首轮基线出来后冻结分项目门槛。建议讨论的首期目标为和弦身份首选命中率 ≥90%、盲推终止“类型及落点”F1 ≥0.90、错误/警告查准率 ≥95% 且已标应报样本召回率 ≥90%。同时约定最低标注覆盖与各类最小样本量，公布未覆盖题材以及严格范围分数。 |

试点先做 CLI、证据记录、抽检和现有审计包的对接。成熟后可将同一组接口暴露给 MCP。此阶段测量的是对既有答案的分析能力；给定旋律或低音自动补全其余声部，另建生成与验证任务。
