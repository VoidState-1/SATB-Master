# SATB Master 项目开发主线

记录日期：2026-11-17。

后续开发围绕自动解题、问题追踪、规则测试和供 AI 使用的 MCP 工具四条主线展开。测试校准规则，日志解释判断过程，推导系统在这些约束下生成并验证答案，MCP 工具让 AI 能调用项目能力开展创作与调试。

## 已确认需求

用户确认的四条主线为：

1. 完善推导系统，实现自动解题。
2. 完善日志系统，高效追踪报错原因。
3. 补充足够的规则测试用例。
4. 开发供 AI 使用的 MCP 工具，包含创作与调试功能。

四条主线均有待开发或继续完善。下面的细化范围与验收方向是对需求的理解和实施建议；题型、工具范围、优先级、量化指标和版本安排在后续任务中确定。

## 完善推导系统并实现自动解题

目标是让系统根据题目条件与和声规则生成可用答案，并解释关键选择。自动解题需要在现有和弦识别、候选推导、乐句分析基础上，进一步处理未完成的题目、生成待填写内容，并通过规则检查验证结果。

当前入口为 [和弦推导](../src/domain/harmony/inference/inferChords.ts)、[完整和声推导与应用](../src/domain/harmony/inference/harmonyInference.ts)；现有流程主要从已有音符推导和弦与乐句结构。实现边界见 [自动分析文档](../Docs/analysis-inference.md)。

建议细化为：

- 明确题目输入、已知条件、允许修改的内容及答案目标。首批可考虑给定旋律或低音补全四部和声，具体题型需另行确定。
- 在调性、和弦功能、节奏、声部进行、乐句和终止式约束下生成候选，搜索整体连贯的解答。
- 区分必须满足的约束与用于比较答案的偏好；规则配置及特例口径与检查系统保持一致。
- 对生成结果重新执行规则检查，保留候选比较与关键选择的依据；存在歧义时允许多个合理答案。
- 区分找到答案、约束冲突、信息不足和搜索达到限制。达到搜索限制不能直接宣称题目无解。
- 提供结果预览与应用，遵守锁定和可编辑范围，并可撤销本次应用。

建议验收方向：在明确的首批题型和经人工校准的题库上，能完成解答、验证规则并解释结果；不能完成时能定位冲突条件或搜索受限的原因。正确率、耗时及题目规模需随题型一起确定。

## 完善日志系统并追踪报错原因

目标是从用户反馈快速还原“当时输入是什么、系统经过哪些判断、为什么得到这个结果”。追踪范围应覆盖程序异常、和声误报、和声漏报及推导失败。

现有 [诊断与调试报告](../Docs/diagnostics-and-debugging.md) 已提供结构化证据、状态跟踪和详细报告，可作为扩展基础。漏报没有现成诊断对象，因此还需要能够按工程范围与目标规则追踪未命中的原因。

建议细化为：

- 关联应用版本、工程 revision、操作或推导批次、规则 ID、配置以及相关音符、和弦和时间范围。
- 跟踪输入与分析事实、规则适用性、命中或跳过原因、状态转移及诊断仲裁，能说明结果为何出现或消失。
- 为推导记录候选生成、淘汰理由、评分、路径选择及停止原因，便于定位错误发生的阶段。
- 为程序异常保留错误堆栈、所属模块与相关操作；统一关联主进程、渲染进程和 Worker 中的相关事件。
- 支持复制或导出足以复现问题的报告，并关联必要的输入快照，减少来回索要信息。
- 控制日志等级、体积、保留期限和性能开销；导出工程内容和本地路径时明确范围，默认保持本地记录。

建议验收方向：面对一次误报、漏报或异常，能够从报告追溯输入、执行路径与原因，并构造最小复现；“规则未启用”“上下文不足”“执行异常”和“确实未违反规则”应有可区分的记录。

## 补充规则测试用例

目标是让规则判断有可核对的音乐学依据，并让后续修改及时暴露误报与漏报。用例数量应服务于语义和场景覆盖。

现有基础包括 [规则测试工作台与用例格式](../Docs/rule-testing.md)、[规则金样本目录](../RuleCases) 和领域测试；仓库中的金样本已接入 [Vitest 批量回归](../src/domain/harmony/testing/ruleCases.test.ts)。

建议细化为：

- 建立规则与用例的覆盖清单，记录规则适用条件、已有场景、预期结论及缺口。
- 每条规则至少覆盖应报与不应报场景，并按实际语义补充边界、特例、缺失上下文、配置与跳过行为。
- 重点覆盖书写音高、调性变化、跨小节、延音与重复音、休止、内外声部及规则之间的相互影响。
- 同时验证诊断规则、位置、相关对象与跳过原因；用跨规则集成用例检查仲裁和覆盖关系。
- 为教材例题记录出处、适用条件与人工解释，先校准预期，再固化为金样本。
- 将确认的用户反馈转成最小回归用例，包括反向五八度漏报、小调导音同音异名等已出现问题。
- 随自动解题扩展端到端题库，分别验证输入约束、答案有效性和失败原因。

建议验收方向：规则覆盖清单能明确指出尚缺哪些场景；修复有对应回归用例，批量运行能区分漏报、误报、对象或位置错误与执行异常。测试预期需要独立的人工或教材依据。

## 开发供 AI 使用的 MCP 创作与调试工具

目标是通过 MCP 向 AI 提供可调用的项目能力，让 AI 能读取音乐上下文、执行创作操作、检查结果并追踪问题原因。

建议细化为：

- 创作工具：读取工程、声部、音符、和弦及调性等上下文；创建或修改音乐内容；调用推导与规则检查，并按需要导出成果。
- 调试工具：查询诊断、日志与规则执行过程，追踪误报、漏报和推导失败；运行规则测试，提取或生成最小复现用例。
- 复用现有领域命令、推导引擎、日志与测试运行器，使 AI 操作与应用界面遵守相同的音乐数据约束、锁定与可编辑范围。
- 为调用提供清晰的输入与结构化结果，关联工程 revision 和稳定对象 ID；修改支持批量应用与撤销，并能追溯具体调用。
- 明确工具可访问的工程与资源范围，以及连接、启停和配置方式。首批工具、接入的 AI 客户端与具体接口在实施时确定。

建议验收方向：AI 能完成一次“读取上下文、创作或修改、检查结果”的流程，以及一次“读取问题、追踪原因、运行复现或回归用例”的调试流程；调用结果可核对，修改可撤销，失败原因可追踪。

## 四条主线的协作方式

建议先补齐高风险规则的样本和问题追踪能力，同时推进范围明确的自动解题原型。每次新增推导能力或修复判断问题，都同步完善解释信息与回归用例，逐步扩大可信的解题范围。

MCP 工具复用上述能力，逐步向 AI 开放创作命令、推导、诊断追踪与测试执行，保持应用界面与 AI 调用的行为一致。

后续拆分实施任务时，分别确定首批自动解题题型、首批日志场景、规则覆盖清单、首批 MCP 工具及各自验收标准，再安排版本与优先级。
