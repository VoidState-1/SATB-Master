# 分析算法的外部审计与修复

和弦推导、终止式分析或规则检查出现跨题重复的误判，或连续几次修补只对少数谱例有效时，优先走这条流程。Gemini 提出可能的根因，主 Agent 对核实、修复和验收负责。教材建库、逐例校准和已知机制的细节优化继续使用[教材谱例校准工作流](./textbook-case-workflow.md)。

## 由用户转述 Gemini 审计问题

主 Agent 在当前对话中给出一段可直接复制的问题和所需材料清单，由用户手动向 `Gemini 4 neon` 提问并转回意见。补问也经用户转述。用户已带回意见时，主 Agent 直接开始独立核实。架构或实现审计可提供对应版本的源码、默认入口、开发集统计和有代表性的输入输出。说明检查点、统计分母及允许逐题查看的范围，请 Gemini 指明可复现的位置、可能的根因，以及什么证据会推翻它的解释。

需要独立乐理判断时，由 Sol 另备中性谱面材料，保留上下文，隐去答案、程序诊断和候选结论。将附件或仅含本次材料的本地目录交给用户，方便选取和转发。记录能够确认的阅材范围，注明用户带回的是原始答复还是转述摘要。接触过诊断或候选解释的回执标明为定向审计。材料准备与子智能体选用见[仓库协作规范](../Agents.md)。

## 独立核实

主 Agent 分别核实意见中的现象、原因和拟议改法。旧版本的统计先核对原检查点和分母，再在当前默认入口复现。涉及音乐正误时查原谱、实际声部和教材条文；涉及算法归因时追到程序真正收到的输入。开发集、验证集和封存集沿用既有边界，只有汇总权限的材料按汇总引用，逐题复算注明实际覆盖范围。

优先做能区分两种解释的验证。例如，怀疑误报来自和弦标注时，固定音符、节奏和声部角色，只替换和弦轨，同时核对出问题的拍位是否真的有标注。分别记下哪些主张成立、哪些被反例推翻、哪些仍缺证据。外部报告部分成立时，已证实的根因可以单独修复。仍可查证的疑点由主 Agent 继续取证；查清后仍需选择教学评分尺度或在多种合理读法中定夺的，按根因归入争议池交人工审计，继续处理其余问题。

## 修复与验收

开发任务中，主 Agent 对已证实的问题直接实施修复。先写清学生在哪个拍位、哪个声部应看到什么结果，再决定改推导、共享的音乐事实、规则本身或诊断归属。若根因在默认判据，连同依赖该判据的旧测试一起复核。例如，同声部变化半音可以是合法写法；若某个既有解释失效，仍须指出有依据的具体违例（如错拼或错解），才能把该处列为应报警的回归样本。

用合法原例和有教材依据的近似错例成对验证，按实际影响从默认入口复测。同一批冻结输入比较前后结果，交代误报、漏报和跳过位置，以及相关模块的连带变化。规则迁移时，核对真实错误仍能在正确声部和拍位得到明确提示。按独立根因提交，结构整理与音乐判断变化尽量分开。分母、样本和代码维护的口径见[教材规则检查器的迭代约定](./textbook-rule-calibration.md)。

用户转回的 Gemini 意见、主 Agent 的独立结论、复现材料及提交与复测结果关联保存在本地 `StandardCase/Pilot/`。教材用例晋升和里程碑验收沿用[原有流程](./textbook-case-workflow.md)。
