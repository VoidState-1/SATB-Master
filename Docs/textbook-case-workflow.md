# 教材谱例转写、比对与人工审计

本流程按用户在 2026-11-17 明确的要求分成两个阶段。第一阶段产出可追溯的候选数据和分析报告; 第二阶段整理问题、提交人工审计和解决方案, 审阅通过后执行相应修复。模型判断、教材依据和测试通过均不能自行替代人工审阅。

数据入口见 [SATB 简写接口](./score-text.md), 批次目录见 [StandardCase](../StandardCase/README.md)。

## 第一阶段: 识读、自检、推导比对与诊断记录

### 1. 转写和独立标注

- 记录书名、版本、PDF 页码、书内页码、题号、谱例范围与完整裁图。相邻正文是否属于本题也应核实。
- 转写调号、拍号、四声部、绝对书写音高、时值、起奏、延音与休止。保留初稿和疑点, 不依据“和声应该这样”改读模糊音符。
- Agent 自行标注和弦、用途、和弦外音、乐句和终止式; 区分教材明示标签与模型分析。缺少上下文时保留未知, 不补造确定结论。
- 标注作为 `.satbt` 的独立 `reference` 保存; 保留初始判断, 再执行推导。需要时安排另一 Agent 独立复核, 不要求每例固定使用多个 Agent。

### 2. 推导与模型相互校验

运行和弦与终止式推导, 与 Agent 的标注比较。无答案和弦推导不读取参考和弦; 终止式检测若使用已知和弦或人工乐句, 必须明确这些条件, 不能计成完整自动解题能力。

对分歧回到原图、自身分析和程序证据, 分别检查:

- **转写问题:** 音高、临时记号、声部、节奏、延音、题目归属等是否读错。
- **标注问题:** 和弦功能、用途、乐句划分、终止类型或范围是否判断有误。
- **疑似程序问题:** 输入可靠, 但候选、推导路径或输出信息可能错误、缺失或受工具阻塞。
- **表示或规则口径问题:** 同一音乐事实采用不同范围、命名或适用条件。
- **上下文不足或无法裁定:** 保留双方判断及缺失信息, 不强行达成一致。

模型可以纠正有原图或音乐依据支持的转写与候选标注, 每次记录旧值、新值、理由和依据。程序与模型一致不等于正确, 不一致也不等于程序错误; 不为了提高匹配率调整原谱、默认参数或参考答案。

### 3. 确认转写后运行规则检查

教材报错率的读法、应报样本的构造和跨轮汇报约定见[教材规则检查器的迭代约定](./textbook-rule-calibration.md)。

Agent 自检确认谱面转写忠实后, 才进入规则检查, 并记录确认范围。若音符仍未辨清, 该例停留在识读待定状态; 不输出确定的规则结论。已确认音符但语义标注有多种解释时, 可分别检查并标记结果所依赖的假设。

参考答案通常可作为可靠起点, 但不是绝对正确的证明。规则检查的全部诊断都进入报告, 包括可能正确的建议、疑似程序误报、疑似参考答案错误和未决判断。没有诊断也只表示本次已启用规则没有报告问题。

不得因作品体裁或参考答案身份整体排除诊断。可以记录“规则可能不适用于此体裁/上下文”的分析, 供第二阶段审计。编译失败、未运行、规则跳过与零诊断须分开记录; 不能以空数组表示通过。

### 4. 严重程度与理论依据

| 程序层级 | 分析口径 |
| --- | --- |
| 错误 `error` | 采用较严格的斯波索宾标准, 逐项核实违反条件和明确例外; 不因答案书给出了该写法就直接豁免 |
| 警告 `warning` | 同样采用较严格标准, 说明上下文、触发条件与例外是否成立 |
| 建议 `suggestion` | 可采用较宽松的教学或审美容差, 判断其是否只是值得关注的写法; 允许提出保留建议、调整适用范围或无需修复的意见 |

原始严重程度保持不变。模型对结论的置信度另记, 不以“较确定”代替错误等级, 也不以“建议较宽松”为理由自行关闭规则或降级。

只要模型判断存在规则口径问题, 必须寻找并记录支撑依据。优先查工作区提供的斯波索宾教材版本, 必要时查询网络的一手教材、作者或院校资料。报告应包含:

- 本地书名及版本、PDF 页与书内页、章节和例号; 网络资料记录标题、作者/机构和直接链接。
- 依据的要点, 及它如何对应当前调性、和弦类型/转位、声部、排列、终止位置等条件。
- 适用边界与尚未证明的部分。一般连接的许可, 不能自动证明所有结尾、声部或七和弦情形都适用。
- 是否存在反向依据; 找不到足够依据时明确写“未找到/仍不确定”, 不猜造出处。

怀疑参考答案有误时, 保留教材原谱和忠实转写, 将模型建议的更正另列为待审意见, 不覆盖来源。

### 5. 阶段一交付与边界

每例提交来源图、候选 `.satbt`、转写自检状态、推导输入条件及原始结果、差异分析、全部规则诊断、证据与未决项。报告至少包含:

| 字段 | 内容 |
| --- | --- |
| 定位 | 批次/案例 ID、来源页/题号、小节拍点、声部和音符 |
| 环境 | 程序版本或代码快照、输入哈希、推导参数、规则档与实际严重程度 |
| 谱面状态 | 已自检确认或未确认的范围、转写修订记录、所需上下文 |
| 双方结论 | Agent 的独立判断、程序输出、实际差异及其属性/范围 |
| 诊断 | 规则 ID、层级、位置、消息和相关证据; 执行阻塞/跳过单列 |
| 模型归因 | 转写/标注问题、疑似程序错误、疑似答案错误、口径差异、上下文不足或未决; 可并列假设 |
| 依据和置信度 | 教材或网络出处、适用条件、模型把握及缺失证据 |
| 待审事项 | 需要人工回答的具体问题, 不只写“请检查” |

第一阶段不修复程序、不改规则标准/严重程度/例外、不把候选预期直接晋升为人工核准金样本。发现确定性很高的工程错误也先记录和复现, 交第二阶段处理。

## 第二阶段: 汇总、人工审计、方案审阅与修复

1. **冻结批次报告:** 保留各次输入与结果, 汇总所有未决判断和原始诊断。统计案例数、自检未确认数、各严重程度的诊断数、未决项数、受影响案例数与问题组数, 分母与运行条件须明确。
2. **归并同类问题:** 按音乐机制或工程根因归类, 保留关联案例及证据。同一规则 ID 的“内声部导音下行至五音”与“次中音三音跳进”应分组, 不能因告警文字相同而套用同一例外。
3. **交人工审计:** 请人工核准谱面/标注, 裁定教材答案疑点、理论依据和严格/宽松口径。模型的初判与人工结论分别保存; 可以只核准明确的部分, 将其余保持待定。
4. **提交具体解决方案:** 对需要修改的组, 说明根因、影响案例、拟改模块、精确适用条件、预期行为、保持严格的边界和正反例验证方案。区分修程序、改候选数据、调整规则口径、补能力或无需修改。
5. **审阅通过后执行:** 记录人工批准的方案与范围后才修复程序、调整规则或固化相关预期。人工仅核准识谱不代表批准程序方案; 明确批准过的范围无需重复请求。未批准、退回补证或有争议的部分不实施。
6. **修复后复测与入库:** 使用已核准预期和同一输入基线比较结果, 补对应回归, 检查跨调、内外声部、缺音、信息不足等边界, 将实施与验证结果回填本地报告。仅将核准且验证过的最终教材用例放入 `StandardCase/Verified/` 供 Git 保存。

`reference complete=...` 只表示参考覆盖完整性, 不表示已获人工批准。人工状态单独记录为“待审/部分核准/已核准/退回补证”, 方案状态单独记录为“待审/通过/拒绝/已实施”。测试通过不能替代任一审计状态。

## Git 与本地材料的边界

- `StandardCase` 默认忽略, 只允许目录说明、已有工具示例 `Samples/` 和最终教材用例 `Verified/` 纳入 Git。
- 原 PDF、裁图、转写草稿、候选谱例、逐次运行输出、分析/审计报告和补丁副本保留在 `Origin/`、`Pilot/` 等本地目录。
- 最终用例只保留复现所需输入、核准预期、必要条件、来源和确认信息; 不夹带整批分析过程或重复生成物。
- 人工核准与验证之前不移动候选到 `Verified/`, 不强制添加被忽略材料。核准数据不等于已验证程序行为, 两步完成后才提交最终版本。
- 应报错反例可作为验证过的最终用例; “已验证”不是“没有诊断”。

## 现有工具与首批试验的衔接

### 批量评测入口

在仓库根目录运行以下命令。每次指定一个新输出目录，旧版本和新版本可使用同一份清单。

```powershell
npm run benchmark -- --manifest <本地清单.json> --out <新目录>
npm run benchmark -- --manifest <本地清单.json> --out <旧版输出目录> --engine-root <冻结的源码根目录>
```

清单的 `cases` 数组逐题提供 `id`、原题键 `parentQuestion`、转写文件 `sourceFile` 和转写确认记录 `analysisFile`。输入路径以仓库根目录为基准。可同时提供 `sourceSha256` 和 `analysisSha256` 校验冻结的文件。只有原谱明确更换调号时，才在 `printedKeyChanges` 列出题内对应的“小节:拍”位置。盲推只用四声部和题面节拍、调号。条件终止使用已标和弦与乐句，条件规则还可使用已标终止。缺少连续和弦覆盖而无法使用的终止会写入逐题记录。

和弦按参考覆盖时值评价首选，各原题等权结果另列。终止按类型和区间右端一对一匹配，仅在声明 `reference complete=cadence` 的原题汇总精确率与 F1，部分覆盖题只对已知标签统计命中。规则默认报告诊断量。已有独立预期时，可为某题添加如下局部断言。拍位使用从工程起点计的整数 tick，声部集合精确匹配。

```json
{"mode":"conditioned","ruleId":"voice.crossing","tick":0,"voiceIds":["soprano","alto"],"severity":"error","expected":"absent"}
```

把这些对象放入该题的 `ruleAssertions` 数组。`mode` 可选 `conditioned` 或 `blind`，`expected` 可选 `present` 或 `absent`。两条路径各自统计已核验位置的 TP、TN、FP、FN 和剩余未核验诊断。题库缺少应报样本时，召回率为空。

输出包括 `environment.json`、`summary.json` 和 `cases/<id>/` 下的原始推导、参考、输入副本与诊断。比较不同引擎时，核对清单、运行器、输入、规则档与参考内容一致，受限输入和执行异常单列。教材派生的输出和人工待审预期保存在本地忽略目录。
